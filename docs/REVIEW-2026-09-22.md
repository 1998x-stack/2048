# 2048 source review and optimization — 2026-09-22

## Scope and baseline

Reviewed the default-branch source tree (`src/`, `config/`, six existing standalone test suites, test runner, README, and the previous 2026-08-19 optimization plan). The project is an 8×8 Pygame 2048 variant with a non-classic, decreasing-weight spawn distribution; preserving this documented variant is intentional. This change does not add score tracking, change tiles' probabilities, or redesign the UI.

## Confirmed findings and changes

| Priority | Finding | Change in this PR |
| --- | --- | --- |
| High | `is_game_over` constrained checks to `min(len(grid), GRID_SIZE)` and used the same bound for columns, so a nonconfigured board could be partly ignored. | Check actual board cells and adjacent neighbors in `src/board.py`; add non-8×8 regression checks. |
| High | Terminal state was evaluated only after draining all queued input events; multiple queued moves could take place after reaching 2048. | Evaluate initial board and re-evaluate after each valid move in `src/game.py`; ignore subsequent moves when terminal. |
| Medium | Domain rules, random spawning, font cache, and Pygame rendering lived in one module, forcing tests and future bot clients to import rendering dependencies. | Extract the board rules to Pygame-free `src/board.py`; retain the existing imports through `src/game_logic.py` re-exports. |
| Medium | `logging.basicConfig` could modify the host application's root logger, depended on the current working directory, and did not rotate files. | Use one named nonpropagating logger and a bounded rotating handler with an absolute default log path. |
| Medium | `run_tests.sh` hid stderr and truncated per-suite output; failures were hard to diagnose. | Show full output, stop on failure, add pure-board and logging suites. |
| Medium | No repository Actions workflow verified proposed changes. | Add Python 3.11 syntax and headless test workflow for pull requests and pushes to `main`. |
| Low | README described the generator as Poisson and listed NumPy although the current implementation uses neither. Runtime log was tracked. | Correct README and stop tracking generated logs and rotated backups. |

## Compatibility and validation

Existing `src.game_logic` function names remain importable (`merge_row`, `move_left/right/up/down`, `_spawn_weights`, `add_random_tile`, `get_max_value`, `is_game_over`, `draw_grid`, and font helpers). The 8×8 UI, victory threshold, first two spawns, and per-valid-move spawn remain. `add_random_tile` now additionally supports an optional independent RNG for reproducible simulations without modifying the process-wide RNG.

Locally verified the **10 newly added pure-board unittest cases** and **1 logger unittest case**. Python compilation was also checked for the newly constructed pure modules. Full pre-existing Pygame/render/integration suites were **not run locally**, because Pygame is not installed in this execution environment and the remote Git repository could not be cloned by the local shell. The new GitHub Actions job runs the complete script in a headless environment; its status should be checked before merging. Do not interpret the local 11-test result as proof that all existing GUI tests passed.

The updated test runner defaults to the SDL dummy video and audio drivers. The six existing suites run in independent Python processes; this matters because the original `test_game_logic.py` injects a temporary `pygame` stub.

## Follow-up work (separate PRs)

1. **Integration regression**: add a deterministic queued-input Pygame test proving that after a winning move, later queued arrow events cannot change the board; run on CI before merge.
2. **Module packaging**: standardize entry points and `sys.path` bootstrap across `config/settings.py`, `src/utils.py`, `src/assets_loader.py`, `src/event_handler.py`, and `src/player.py`; move existing standalone tests to a consistent unittest/pytest style. Avoid broad import changes without an executable Pygame environment.
3. **Formal move model**: if adding scoring, return merge points separately from the existing bool movement API so consumers remain backward compatible; add undo snapshots and move histories if desired.
4. **Rendering and accessibility**: validate large font glyph fit, overlay contrast, keyboard repeat behavior, and resizable window layout with a GUI-capable test runner.
5. **Production hardening**: refine log setup for unwritable directories and optional diagnostics fallback; inspect asset attribution/licensing and add release instructions.
